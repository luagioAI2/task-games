## 1. 运行时骨架

### 1.1 没有构建步骤

这是理解整个项目的前提：**源码就是浏览器直接执行的文件**。没有 webpack/vite，没有 TS 编译，没有 tree-shaking。

```
index.html
  ├─ <script type="importmap">     裸模块名 → 本地路径
  ├─ platform-stub.js              平台 API 垫片（classic script，先执行）
  └─ game.js  (type="module")      入口
```

`index.html` 只做三件事：装 importmap、装平台垫片、挂 `game.js`。所有 UI 都是 JS 里 `innerHTML` 拼出来的，HTML 文件里除了 `<div id="app">` 什么都没有。

### 1.2 模块解析链

原站把引擎放在 CDN 上，用 importmap 映射：

| 裸名 | 原指向 | 本地版指向 |
|---|---|---|
| `three` | `makeplay.ai/engines/three.module.js` | `./engines/three.module.js` |
| `three/addons/` | `makeplay.ai/engines/three-jsm/` | `./engines/three-jsm/` |
| `@dimforge/rapier3d-compat` | `makeplay.ai/engines/rapier3d.mjs` | `./engines/rapier3d.js` |
| `@makeplay/fx` | `makeplay.ai/runtime/makeplay-fx/game.js` | `./runtime/makeplay-fx/game.js` |
| `@makeplay/sound` | `makeplay.ai/runtime/sound-1.js` | `./runtime/sound-1.js` |

只有 5 个入口被真正用到，importmap 里其余（pixi / phaser / rapier2d / glyph / display）是平台给所有游戏准备的公共表，这个游戏没引用。

**关键约束**：ES Module 在 `file://` 下会被 CORS 拦死，必须走 http。这也是本地版必须带 `server.js` 的原因。

### 1.3 启动顺序

```
1. 同步执行 game.js 顶层
   ├─ 建 renderer / scene / 灯光 / 相机 rig
   ├─ 拼 CSS（一个 <style> 字符串，约 400 行）
   ├─ 拼 DOM（innerHTML，7 个 screen + 5 个弹层）
   ├─ loadSave()  ← 读平台存档，跑 3 段迁移逻辑
   ├─ ensureDaily() ← 检查是否跨天，跨了就重抽任务
   ├─ 绑定输入 / 菜单 / 屏幕切换
   └─ 启动 requestAnimationFrame 主循环
2. 异步 IIFE
   ├─ await RAPIER.init()        ← 解 base64 内嵌的 wasm
   ├─ new World / EventQueue
   ├─ loadSoundSystem(manifest)
   ├─ gp.player.ready.then(...)  ← 拿用户 locale 覆盖语言
   └─ playable = true
3. 主循环里 if (!inMachine || !world) return  ← 未就绪就空转
```

`window.__gpPlayable` 是就绪信号，也是最好的自动化测试锚点。

## 2. 三层职责划分

虽然没有模块化，但代码里有清晰的三层，只是挤在一个文件里：

| 层 | 内容 | 特征 |
|---|---|---|
| **纯逻辑层** | `config.js` `i18n.js` `daily.js` `market.js` | 无 DOM、无 three、无 Rapier，纯函数 + 数据表，**可以直接单测** |
| **模拟层** | Rapier world、`craneTick`、`simulate` | 只依赖数值，不碰 DOM |
| **表现层** | three 场景、DOM 界面、音效、特效 | 单向从模拟层读状态 |

状态只有一份：模块级 `save` 对象 + `persist()`。没有 Redux，没有响应式，改完数据手动调 `refreshTexts()` / `buildCards()` 刷新。

## 3. 渲染层

### 3.1 Renderer 参数

| 参数 | 值 | 说明 |
|---|---|---|
| antialias | true | |
| pixelRatio | `min(devicePixelRatio, 2)` | 上限 2，防止 4K 屏爆显存 |
| shadowMap | PCFSoft | 2048×2048，正交阴影相机 ±4.5 |
| toneMapping | ACESFilmic，exposure 1.05 | 让粉紫色不过曝 |
| clearColor / fog | `0xf6eef8`，Fog(14, 30) | 淡紫白，远景融进背景 |
| 后处理 | **无** | 没有 EffectComposer，全靠 tone mapping + emissive |

### 3.2 光照配置（4 盏，全是固定值）

```
HemisphereLight(cream #fff3d8, lavender #a995ff, 0.9)   ← 环境主光，冷紫打底
DirectionalLight(#ffffff, 2.4)  pos(3, 9, 5)  投影      ← 唯一投影光源
PointLight(pink #ff8fb8, 6, 距离14)   pos(-4, 4, 3)     ← 左侧粉色边缘光
PointLight(mint #7de2d1, 6, 距离14)   pos(4, 3, -3)     ← 右侧薄荷边缘光
```

双色边缘光是这套画面的灵魂：粉在左、薄荷在右，把白柜体从背景里"抠"出来。换配色只要换这两个颜色。

### 3.3 相机 rig（自适应，非固定）

不是写死机位，而是按机台尺寸和屏幕比例**反算距离**：

```
1. 目标水平视场 42° → 反推垂直 fov：
   vfov = 2·atan( tan(42°/2) / aspect )
   clamp 到 [28°, 78°]（竖屏手机上 fov 会被拉很大，必须钳住）
2. 算包住机台所需的距离：
   halfW = (前视 ? caseW/2 : caseD/2) + 0.9
   halfH = caseH/2 + 0.75
   d = max( halfW / tan(hfov/2), halfH / tan(vfov/2) ) × zoom
3. 前视机位：pos(0, caseH·0.44 + d·0.3, d)
   侧视机位：pos(d, caseH·0.44 + d·0.28, 0.5)
   注视点：  (0, caseH·0.44, 0)
```

切机位是 0.3s 的二次缓动 tween；之后每帧用 `lerp(goal, dt·10)` 跟随，所以缩放窗口时相机是"黏"过去的。

`ResizeObserver` 监听的是 `#viewport` 而不是 window——因为横屏时 `#viewport` 只占右半边。

### 3.4 材质表（7 个共享材质，全场景复用）

| 名称 | 参数 | 用在哪 |
|---|---|---|
| matCabinet | `#f7f4fa`, rough 0.55 | 柜体、立柱、顶盖 |
| matAcrylic | `#dde9ff`, opacity 0.14, DoubleSide, depthWrite:false | 三面玻璃 |
| matSteel | `#cfd3e0`, metal 0.7, rough 0.35 | 横梁、缆绳、爪指 |
| matFloor | `#fff3d8`, rough 0.8 | 柜内底板 |
| matBackWall | `#fbf6ff`, rough 0.9 | 背板 |
| matChute | `#3b3556`, rough 0.9 | 落口内壁（深紫，制造"洞"的感觉） |
| glowPink / glowMint | 同色 emissive，强度 1.6 | LED 灯条 |

`matAcrylic` 的 `depthWrite:false` 很重要——否则玻璃会挡住里面的奖品。

### 3.5 场景图结构

```
scene
├─ machineGroup (每次进机台重建)
│  ├─ 底板 / 四壁 / 顶 / 立柱×4
│  ├─ 玻璃×3 (前/左/右)
│  ├─ 背板 + popGroup (海报平面，可多个 slot)
│  ├─ 落口 (四壁 + 底 + 发光条 chuteGlow)
│  ├─ 横梁 beamMesh + 缆绳 cableMesh (每帧跟着爪头伸缩)
│  ├─ headMesh (爪头，每帧同步位置)
│  ├─ 爪指 mesh×N (每帧同步刚体)
│  ├─ shadowBlob (地面椭圆假影，每帧贴到"爪下最高面")
│  ├─ 周边：地板/天花板/灯带/邻机×7/招牌
│  └─ debugGroup (线框，TEST 菜单开关)
├─ prizes[].mesh (每个奖品一个 Group)
├─ balls[].mesh (章鱼烧球)
└─ staffHand (补货的手，平时不在场景里)
```

### 3.6 一个容易忽略的细节：假影

`shadowBlob` 是一个 `CircleGeometry` + 半透明黑，每帧：

```
1. 找爪头正下方 0.45 半径内最高的奖品顶面
2. 贴到那个高度 + 0.008
3. 缩放 = 0.55 + 0.12 × (爪高 − 面高)
4. 透明度 = 0.34 − 0.04 × 高度差
```

这不是装饰。**没有它，玩家在 2D 屏幕上判断不了爪子和奖品的 z 轴距离**——3D 抓娃娃最容易劝退的点就在这。

## 4. 物理层

### 4.1 引擎与初始化

`@dimforge/rapier3d-compat`（Rust → wasm）。wasm 以 **base64 字符串内嵌**在 `rapier3d.js` 里（约 2.09MB 的字符串常量），`RAPIER.init()` 走 `toByteArray()` 解码，**不发起网络请求**。所以这一份引擎文件拷贝走就能离线跑，不需要额外 `.wasm`。

源码里有一句 `new URL("rapier_wasm3d_bg.wasm", "<deleted>")` 是死代码（构建时被替换掉了），不要被它误导去找 wasm 文件。

### 4.2 时间步进

```
固定步长  fixedDt = 1/120 s
单帧上限  maxStepsPerFrame = 8
实际步数  n = clamp( round(dt / fixedDt), 1, 8 )
子步长    h = min( fixedDt × 1.5, dt / n )   ← 命中顿帧时 h 会变小，物理跟着变慢
```

`dt ≤ 0.0005` 时直接 return。**这一行是保命的**：零时间步会让 Rapier 内部 panic，而 wasm panic 之后整个物理引擎就废了，只能刷新页面。

### 4.3 碰撞分组（位掩码）

```
GROUP_STATIC = 0x0001   柜体、横梁、落口、桥杆
GROUP_PRIZE  = 0x0002   奖品刚体
GROUP_CLAW   = 0x0004   爪头、爪指

编码方式：(membership << 16) | filter
```

三个用途：

1. **爪子穿模控制**：`setClawPassThrough(true)` 时把爪子的 filter 从 `STATIC|PRIZE` 改成只有 `STATIC`——爪子不再和奖品碰撞。用在"奖品已判定成功、要放它走"的时候，否则爪指会把奖品挂住不放。
2. **GET 后隔离**：`startSuck` 里把奖品 filter 设成 `0`，谁都不碰，让它安安静静滑进洞口。
3. **休眠奖品**：`parkPrize` 把碰撞体 `setEnabled(false)` **并且**把刚体搬到 y = -30。**两个都要做**——这个版本的 Rapier 里，disabled 的碰撞体仍然会产生 contact 事件。

### 4.4 每帧执行顺序（顺序错了会出 bug）

```
for step in 1..n:
  1. restockTick        ← 店员补货动画（桥机）
  2. craneTick          ← 状态机推进，写 crane.x/y/z
  3. 速度钳制            ← linvel ≤ 7, angvel ≤ 12（防止炸飞）
  4. world.step(eventQueue)
  5. drainEvents        ← 碰撞事件 → 火花/音效
  6. 逐奖品：
       safetyTick      ← 出界复位（存了 safe 位置）
       GET 判定         ← 四种规则之一
  7. 同步 mesh 位置/朝向
```

注意 `craneTick` 在 `world.step` **之前**：状态机写的是 `clawHead.setNextKinematicTranslation(...)`，Rapier 要在下一步才知道爪子去哪。反过来就永远慢一帧。

### 4.5 三处"防炸"设计

| 问题 | 处理 |
|---|---|
| 奖品被挤出柜子 | `safetyTick`：超出 `caseW/2+0.6` 就瞬移回 `safe` 点（每 0.5s 记录一次合法位置） |
| 速度爆炸（穿模/挤压） | 每步钳制线速度 7、角速度 12 |
| 盒子穿透（桥机） | 刚体开 `setCcdEnabled(true)`（连续碰撞检测） |

## 5. 机台构建系统

### 5.1 参数化：一台机 = 一个 config 对象

所有机台共享 `baseMachine` 默认值，各自覆盖差异项：

```
caseW/caseD/caseH   4.8 / 4.0 / 5.2     柜体尺寸（米）
chute               {cx, cz, w, d, depth} 落口位置与大小
home                {x, y, z}           爪头待机点
limits              {xMax, zMin}        移动边界（只做正方向限制）
speedX/speedZ       0.8 / 0.62          水平速度
accelTime/decelTime 0.15 / 0.10         加减速时间
descentDistance     3.65                下爪行程
descentTime         2.0                 下爪耗时
closeTime/holdTime  0.7 / 0.45          合爪 / 停顿
liftTime/homeTime   2.0 / 2.5           上升 / 回位
releaseTime         0.6                 松爪
settleMax           3.0                 静置等待上限
armPower            1.0                 握力系数 ★核心手感参数
armWidth            0.16                两指间距
fingerLen           0.82                指长
openAngle/closedAngle  0.95 / -0.22     开合角度（弧度，负=向内扣）
claws               2 或 3              爪指数
kind                grab|bridge|takoyaki|sweets   玩法内核
prizes              [{pos, rot, weight, friction, centerOfMass, grabPowerModifier, scale}]
pops                {main, sub1, sub2}  背板海报 {image, x, y, width}
led                 {a, b}              LED 双色
```

**加一台新机只要往 `MACHINES` 数组里加一个对象**，不用碰 game.js——这是这套代码最大的价值。

### 5.2 碰撞体布局（柜体）

固定刚体，全部 `cuboid`：

```
底板：落口周围拼 4 块（留出洞）——左右各一块、前后各一块
     ← 不是一整块挖洞（Rapier 没有带洞的 box），而是拼贴
洞沿：4 条 0.02 高的"滑边"，摩擦 0.05
     ← 故意滑，让玩偶碰到边缘就滑进去，而不是停在边沿
四壁：厚 0.1，高 H/2+1（比柜子高一米，防止奖品被顶出去）
顶盖：一块
落口井：4 壁 + 底（depth=2.3m 深，底摩擦 0.9 让奖品停下）
```

### 5.3 抓爪的两种实现

**A. 两指（标准机 / 桥机 / 零食机）**

- 刚体：dynamic，`linearDamping 2`，`angularDamping 2`，`canSleep false`，开 CCD
- 碰撞体：2 个 capsule（主指 + 折角指尖），density 6，摩擦 1.4（桥机 0.5）
- 关节：`JointData.revolute` 连到爪头，轴 `(0,0,1)`，限制 `[closedAngle, openAngle+0.4]`
- 电机：`ForceBased` 模型，`configureMotorPosition(angle, strength, damping)`

**握力的关键就在这里**：`strength` 不是常数，而是每帧按负载重算：

```
strength = 60 × armPower × tune.armPower × grabPowerModifier × 0.9
off      = 奖品中心到爪轴的水平距离
load     = 奖品质量
eff      = strength × max(0.35, 1 − max(0, off − 0.25) × 1.2)
                     / max(0.6, load / 1.8)
```

翻译成人话：

- **偏心的抓不住**（off > 0.25 开始衰减，最多衰减到 35%）
- **重的抓不住**（load > 1.8 开始衰减，最多到 60%）
- 所以"抓正中间"和"抓轻的"是真有回报的，不是玄学

这就是抓娃娃机的核心手感公式。想调难度就调 `armPower`（0.13 ~ 1.0 之间，桥机 0.13 只能推不能提）。

**B. 三指（抱枕机 / 吉祥物机 / 章鱼烧）**

不是三根直杆，而是**一根连续的弯钩**：

- 视觉：`CatmullRomCurve3` 过 5 个控制点 → `TubeGeometry` 生成钢管
- 物理：沿同一条曲线采样 10 个 `ball` 碰撞体（不可见）
- 好处：视觉是光滑的弯钩，物理是一串球——比用 capsule 拼接近似得多，且不会卡角

三根按 120° 分布（yaw = 0, ±120°）。

### 5.4 奖品构建

**泰迪熊（程序化建模，零外部模型文件）**

纯 `SphereGeometry` 堆叠 + 缩放，参数是手调的：

| 部位 | 位置 | 缩放 |
|---|---|---|
| 身体 | (0, −0.05, 0) | 0.42 / 0.40 / 0.38 |
| 肚皮 | (0, −0.08, 0.2) | 0.26 / 0.26 / 0.20 |
| 头 | (0, 0.62, 0.02) | 0.40 / 0.38 / 0.38 |
| 耳 ×2 | (±0.27, 0.9, −0.02) | 0.12 / 0.12 / 0.09 |
| 口鼻 | (0, 0.53, 0.30) | 0.17 / 0.13 / 0.13 |
| 眼 ×2 | (±0.13, 0.68, 0.40) | 0.05 / 0.055 / 0.04 |
| 腮红 ×2 | (±0.23, 0.56, 0.35) | 0.07 / 0.05 / 0.03 |
| 手臂 ×2 | (±0.40, 0.05, 0.08) | 0.15 / 0.13 / 0.13 |

嘴巴是 `TorusGeometry` 半圆（弧长 π），翻转 180° 当微笑。

**关键技巧**：所有部件**互相重叠**，接缝藏在重叠区里，看起来就是一体毛绒，不需要蒙皮或布尔运算。

**盒子（桥机奖品）**

一张 1536×1024 的"展开图"（正面 | 侧面 | 背面），用 **UV 窗口**切出三块贴图：

```
texture.offset = (x0/W, 1 − y1/H)
texture.repeat = ((x1−x0)/W, (y1−y0)/H)
texture.wrapS = wrapT = ClampToEdge
```

同一个 `Texture` 对象不能同时用不同窗口（offset/repeat 是共享的），所以每面单独 `load` 一次，用 `boxTexCache` 按 prizeId 缓存。

左脸要**镜像**：`repeat.x *= -1; offset.x += repeat.x`。

### 5.5 布局持久化

每次 GET / 补货 / 离场，把每个奖品当前的 `{pos, rot}` 存进 `save.layouts[machineId]`；进场时 `restoreLayout()` 还原。**这样奖品不会每局重置**——符合真实抓娃娃机的体验（别人抓乱了就是乱的）。

## 6. 抓取状态机（核心中的核心）

`crane.phase` 是一个字符串状态机，`craneTick(dt)` 里一个 `switch`。全部状态：

| 状态 | 干什么 | 退出条件 | 时长参数 | 音效 |
|---|---|---|---|---|
| `ready` | 待机，爪张到 openAngle | 点 PLAY | — | — |
| `idle_x` | 等玩家按左右 | 按住方向键 | — | — |
| `moving_x` | 水平移动 | 松手且 v ≤ 0.001 | speedX=0.8, accel 0.15 | crane.motor（每 1.4s 重播） |
| `idle_z` | 等玩家按前后 | 按住 | — | — |
| `moving_z` | 纵深移动 | 松手且 v ≤ 0.001 | speedZ=0.62 | crane.motor |
| `catchgo` | 大字提示"抓！" | 0.8s | 0.8 | catch.go |
| `open` | 爪张到最大 | 0.5s | 0.5 | claw.open |
| `descend` | 匀速下爪，**边下边检测接触** | 触底 / 触奖后再下 0.42 / 到 minClawY | 2.0s 走 3.65m | crane.descend |
| `close` | 合爪 | closeTime | 0.7 | claw.close |
| `hold` | 停顿（让摩擦咬住） | holdTime | 0.45 | — |
| `lift` | 上升回待机高度 | liftTime | 2.0 | crane.descend |
| `home` | 水平回待机点，带轻微上下摆动 | homeTime | 2.5 | crane.motor |
| `align` | **仅 grab 机**：抓到了就锁死并滑到落口正上方 | 0.25s 滑行完 | 0.25 | claw.open |
| `release` | 张爪 | releaseTime | 0.6 | claw.open |
| `settle` | 等所有奖品静止 | 全静止 或 settleMax+2 | 3.0 | — |
| `back` | 回位后短暂停顿，判定成败 | 0.5s | 0.5 | — |
| `get` | 成功，弹结算层 | 玩家点按钮 | — | prize.get |
| `fail` | 失败，显示"再来" | 点 PLAY | — | result.miss |
| `restock` | 桥机补货动画 | 动画结束 | ~2.85s | crane.confirm |

### 6.1 三个不显然的设计

**① `descend` 的"接触后继续下压 0.42"**

触到奖品不立刻停，而是继续往下走 0.42 米再停。目的：让爪指**绕过奖品最宽处**扣住，而不是掐在顶端。这是"看起来抓到了但一抬就掉"和"真的抓住了"的分界线。

桥机例外：接触不减速，一直下到 `minClawY`（1.85），让爪指滑到盒子底部再合——因为盒子太厚，掐顶端必然掉。

**② `align` 阶段的"成功锁定"**

grab 机里，如果回到待机点时爪子还吊着东西，**这一刻就判定成功**，然后：

```
releaseSuccess = true
guidePrize = 那个奖品
奖品刚体 → KinematicPositionBased（脱离物理）
setClawPassThrough(true)         ← 爪子不再碰它
0.25s 内把奖品滑到落口正上方
```

这是个"作弊"设计，但很合理：真实机器里，爪子在回程中抖掉是常事；这里改成**回程不抖，到点必成**，玩家的努力不会白费。代价是要用运动学动画把它送进洞，所以有 `guidePrize` 这套引导逻辑。

**③ `settle` 的"抖落"**

如果奖品还挂在爪上（`y > 2.2` 且靠近爪轴），非 grab 机每帧做小幅正弦抖动（`sin(t·28)×0.05`），1.2 秒后强制 `setClawPassThrough(true)` 让它掉。grab 机反过来——**不抖**，只是慢慢往上抬 5cm 然后等，避免"明明抓到了却被抖掉"的挫败感。

### 6.2 速度平滑

```js
smoothVel(v, target, m, dt, max):
  rate = (target > 0 ? max / accelTime : max / decelTime)
  return v < target ? min(target, v + rate·dt) : max(target, v − rate·dt)
```

不是瞬间到速，也不是指数逼近，而是**线性加减速**。0.15s 加速到 0.8m/s，松手 0.1s 停下——手感上就是"按下去有点惯性，松手立刻停"，符合街机的味道。

## 7. GET 判定：四套规则

不同玩法用完全不同的判定，这是代码里最容易被忽略的复杂度。

### 7.1 grab（抓娃娃）—— 中心点进区 + 吸附

```
条件：
  phase ∈ {release, settle, back, fail, ready}   ← 必须已经松手
  y < 0.75 且 y < 爪高 − 1.2                      ← 在下方，且离爪够远
  |x − chute.cx| < chute.w/2 + 0.18               ← 落在口内（带 0.18 宽容）
  |z − chute.cz| < chute.d/2 + 0.18

判定后：startSuck() → 0.35s 内用运动学把奖品滑到洞口中心并淡出
```

宽容 0.18 是刻意的：玩偶压在口沿上、重心已经过去了，就算赢。玩家看着"它明明掉进去了"，就不该判失败。

### 7.2 通用 —— 8 角点全包含

`prizeInChute()` 取奖品的 8 个包围盒角点，逐个做刚体变换，要求**全部**满足：

```
x 在 [cx−w/2−0.03, cx+w/2+0.03]
z 在 [cz−d/2−0.03, cz+d/2+0.03]
y < 0
```

用于抱枕 / 吉祥物这类需要"整个身体都进去了"才算的机型。

### 7.3 bridge（桥机）—— 中心下坠

```
boxThroughBridge: t.y < −0.3 且 |t.x| < caseW/2
```

盒子只要掉到杆平面以下就算。因为桥机的杆就在 y=0.95，盒子掉下去必然进坑。

### 7.4 takoyaki —— 球进洞

球落到指定的 cup（`getIdx`）里算成功；落到其他 cup 就**留在盘上**，累积起来让后面更容易进——这是个"越玩越容易"的设计。

### 7.5 持续判定

通用规则要求 `inChuteT ≥ getHoldTime`（0.35s）——奖品得在洞里**待够 0.35 秒**才算，防止一帧的误判。

## 8. 四个玩法内核

| kind | 玩法 | 核心机制 | 特有系统 |
|---|---|---|---|
| `grab` | 经典抓娃娃 | 2/3 指爪 + 握力衰减 | 假影、align 锁定、suck 吸附 |
| `bridge` | 桥杆推盒子 | 爪力只有 0.13，**只能推不能提** | 双杆、盒子 CCD、店员补货动画、静置库存 |
| `takoyaki` | 勺子舀球 | 勺倾斜 → 球滚进盘子 18 孔 | 230 个球、球池、孔位物理、越玩越易 |
| `sweets` | 零食堆 | 320 个零食，爪力 0.55，靠"扒拉" | 分层堆叠、批量 GET、汇总弹窗 |

### 8.1 bridge 的精髓：不是"抓"，是"推"

`armPower: 0.13` 意味着合爪的力量远小于盒子重量——抓不起来。玩家的操作是：

1. 爪指插到盒子底下
2. 合爪，把盒子**顶起来一点点**
3. 盒子失去平衡，从两根杆之间掉下去

`descentDistance` 特意跑到杆平面以下（`minClawY: 1.85`），就是为了让指头能伸到盒子底。

### 8.2 takoyaki 的球池模拟

- 230 个乒乓球（半径 0.1），初始堆在左侧池里
- 进机台时**预跑 1100~1400 步物理**让球堆自然落定，然后全部 `sleep()`——否则开场会看到球在抖
- 球的存活保护：掉出界就瞬移回池子或盘上
- 盘上 18 个孔，1 个是 GET 孔。球进普通孔就留在那，盘越来越满 → GET 概率越来越高

这个"累积变易"是它的留存设计，不是 bug。

### 8.3 sweets 的批量结算

320 个零食一次抓可能带出好几个。所以 GET 不立刻弹窗，而是：

```
back 状态 → 等零食堆停止滑动（最多 4s）
          → 汇总这一把带出了哪些、各几个
          → 一次弹窗结算
```

`showSweetHaul()` 就是这个汇总层。

## 9. 经济系统

> ⚠️ **本章写的是原站（MakePlay 版）的经济，仅作逆向记录。**
> 本地副本第 8 条改造已把它整个换掉：删签到 / 印章 / 任务 / 跳蚤市场，
> 改成 **积分 → 娃娃机币 →（玩）→ 奖品 → 兑换券** 的单向道。
> 现行规则以 `README.md` 的「经济」一节为准 —— 特别是
> **奖品只能换兑换券，不能变回娃娃机币**（2026-10-23 起，`host.mintVoucher`）。

### 9.1 三种货币

| 货币 | 来源 | 用途 | 特性 |
|---|---|---|---|
| 🪙 金币 | 初始 3000、每日印章、任务 | 投币玩（100/次） | 会耗尽 |
| 🎟️ 券 | 印章奖励 | 免费玩一次 | 稀缺 |
| ￥ 收益 | 跳蚤市场卖奖品 | **可直接抵扣投币** | 不兑换成金币 |

**付费优先级**：券 > 收益 > 金币。金币不够时会弹"用收益支付"的确认框——**绝不静默扣钱**。

### 9.2 跳蚤市场（价格模拟）

每个奖品有独立行情：

```
每小时漂移一次（离线也补算，最多补 48 步）：
  target = base × (0.85 + popularity × 0.06) × (稀缺 ? 1.6 : 1)
  price  = round10( price + (target − price) × 0.25 + price × 噪声(±8%) )
  popularity 也随机游走，钳在 [1, 5]
```

成交概率是**分段函数**（价格比 = 挂牌价 / 市场价）：

| 价格比 | ≤0.6 | ≤0.8 | ≤0.95 | ≤1.05 | ≤1.2 | ≤1.5 | >1.5 |
|---|---|---|---|---|---|---|---|
| 基础概率 | 0.85 | 0.60 | 0.35 | 0.20 | 0.08 | 0.025 | 0.006 |

再乘三个修正：

```
× (0.6 + 人气 × 0.16)          ← 人气 1~5，影响 0.76~1.4
× (1 + min(0.5, 赞数 × 0.04))  ← 最多 +50%
× 1.8（如果 2 分钟内降过价）      ← "降价通知"效应
上限 0.95
```

**这个设计的精妙处**：便宜不等于"立刻卖掉"，而是"买家来了更可能选你"。买家每 6 秒来一个，从所有在售里随机挑一个看。所以定价策略是真实的：定太低亏，定太高没人要，定 95% 市场价是甜点。

成交抽 10% 手续费。

### 9.3 假市场（demo）

为了"看起来热闹"，市场页永远有 14 个 NPC 在售。它们按 `PRICE_STEPS`（0.78 ~ 1.28 倍）随机定价，按年龄段算售出概率，卖掉后卡片保留 150 秒再换新。

作用是**教会玩家行情**——你看到别人卖 720，就知道自己标 900 没人要。

### 9.4 机台"被占用"

模拟"别的玩家在玩"：

```
每 20 秒检查一次
对每台空闲机台：8% 概率被占用 60~180 秒
硬约束：任何时候至少留 2 台空闲

防霸机（玩家自己）：
  连续玩 5 次 → 离开后锁 120~240 秒
  5 分钟内抓到 3 个 → 离开后锁 5 分钟
  （锁只在离场时生效，不打断当前这局）
```

## 10. 每日系统

### 10.1 时区与重置

```
jstDayKey(now) = new Date(now + 9h).toISOString().slice(0,10)
```

**固定按日本时间（UTC+9）0 点重置**，不看本地时区——因为这是个日式街机游戏。

### 10.2 印章（7 天）

非连续签到，每天可领一次，7 天一轮循环：

| 第几天 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| 奖励 | 50币 | 50币 | 1券 | 70币 | 80币 | 1券 | 2券 |

集满 7 天额外 +100 币（`ALL_CLEAR_BONUS`）。

### 10.3 任务（每天 3 个）

任务池 8 个：

| id | 类型 | 目标 | 奖励 |
|---|---|---|---|
| play1 / play3 | 玩 1 / 3 次 | 1 / 3 | 30 / 50 |
| grab1 / bridge1 | 玩抓取机 / 桥机 | 1 | 30 |
| list1 | 上架 1 件 | 1 | 30 |
| reprice1 | 改价 1 次 | 1 | 30 |
| get1 | 抓到 1 个 | 1 | 60 |
| ticket1 | 用 1 张券 | 1 | 30 |

抽取算法：**先抽 2 个非 get 的（简单），再从剩下的里抽 1 个（可能含 get）**。保证每天不会三个都是硬核任务。

### 10.4 挑战（每天 1 个）

随机选一台机台，两种形式二选一（65% 概率选第一种）：

```
get_within: 在该机台抓到 N 个（桥机 5 / 章鱼烧 8 / 其他 3），奖励 150
play_n:     在该机台玩 3 次，奖励 80
```

### 10.5 种子随机

```js
seeded(dayStr):
  h = 2166136261
  for c in dayStr: h = (h ^ c) * 16777619          ← FNV-1a
  return () => { h = (h ^ h>>>15) * 2246822507; h = (h ^ h>>>13) * 3266489909; ... }
```

用日期字符串当种子 → **同一天所有玩家抽到同样的任务**（离线也能保证），且不用存"今天抽了什么"。

## 13. 音频

### 13.1 不是一堆 mp3，是一个"音频包"

`sound.manifest.json` 描述一切：

```jsonc
{
  "assets": { "music.home": { "variants": { "aac": { "pack": { "id":"main", "offset":0, "length":1176680 } } } } },
  "packs":  { "main": { "url": "sound.pack", "payloadBytes": 2280772 } },
  "cues":   { "claw.close": { "assetIds":["sfx.close"], "bus": "impact", "gainDb": -5, "polyphony": 6 } },
  "buses":  { "master": {...}, "music": {...}, "sfx": {...}, "ui": {...} },
  "musicStates": { "home": { "cueId":"music.home", "crossfadeMs":1400 }, "play": {...} },
  "voicePolicy": { "globalMax": 24, "stealPolicy": "lowest-priority-oldest" }
}
```

16 个音频资产全部打进一个 2.18MB 的 `sound.pack`，用 `offset + length` 寻址。**一次 HTTP 请求拿全部音频**，比 16 个并发请求快得多。

### 13.2 播放 API

```js
sound.unlock()                                  // 首次手势解锁（浏览器策略）
sound.playCue("claw.contact", { eventId, pitchSemitones: ±2 })  // 带随机音高，防重复感
sound.setMusicState("play", { eventId })        // 交叉淡入
sound.settings.setVolumes({ music, sfx })
sound.inspect()                                 // 读当前状态，用于幂等判断
```

### 13.3 BGM 状态机（一个容易写错的地方）

```
musicChain = Promise.resolve()
applyMusic():
  musicChain = musicChain.then(async () => {
    if (musicApplied === musicState) return       ← 幂等
    await sound.setMusicState(...)
    musicApplied = musicState
  })
```

**串行化 Promise 链**。否则"home → play → home"连点三次时，三个异步 crossfade 会并发，最后变成两首 BGM 同时响。这是踩过的坑，代码里的注释明确写了"a slow home→play crossfade can never be overtaken by a stale call"。

| `teleport-light` | 进机台时爪头"通电"闪光 |
| `legendary-reward` | 抓到大奖 |

预设是 JSON 描述：`{id, dimensions, space, placement, priority, semantic, visuals[], impulse}`。`visuals` 里定义粒子形状/数量/速度/生命周期/曲线。

### 14.2 相机冲击（impulse）

```js
fxImpulse = { offsetX, offsetY, roll, fovPunch }

// 渲染前加偏移，渲染后立刻还原
camera.position.x += fxImpulse.offsetX * 0.02
camera.position.y += fxImpulse.offsetY * 0.02
renderer.render(...)
camera.position.x -= fxImpulse.offsetX * 0.02
camera.position.y -= fxImpulse.offsetY * 0.02
```

**关键**：偏移只影响这一帧的渲染，不改相机基座。否则冲击会累积，相机越飘越远。

### 14.3 命中顿帧（hit-stop）

```js
const timeScale = fx.update(realDt)      // 特效拿到真实时间
const gameplayDt = min(realDt, 0.05) * timeScale   // 玩法拿到缩放后的时间
```

命中瞬间 `timeScale` 会短暂降到 0.1~0.3，物理和状态机跟着变慢，但特效本身照常播。这是"打击感"的标准做法，实现只需要一个乘法。

## 15. 平台适配层

游戏只依赖 `window.gp` 的 6 个 API：

| API | 类型 | 用途 |
|---|---|---|
| `gp.player.ready` | Promise\<{user}\> | 等平台初始化，拿 locale |
| `gp.player.user` | `{id, name, locale}` \| null | 用户名、语言 |
| `gp.player.saves.latestSync` | getter → object | **同步**读存档（首帧就要用） |
| `gp.player.saves.putLatest(obj)` | async | 写存档 |
| `gp.player.submitScore(n)` | async | 上传分数 |
| `gp.player.topScores(n)` | async → array | 排行榜 |

本地版 `platform-stub.js` 用 localStorage 实现了这 6 个，`latestSync` 是 getter（不是函数）——这个细节必须对上，否则 `loadSave()` 会拿到 `undefined` 静默失败。

## 16. 用 AI 复刻的施工规格

如果要让 AI 从零写一个同构的游戏，按这个顺序做，每阶段都能独立验收。

### 阶段 1：最小可玩（1 台机，1 种奖品）

**目标**：能投币、能移动、能抓、能进洞。

```
1. 静态服务器 + index.html（importmap 指向 three + rapier）
2. 场景：renderer(ACES, PCFSoft) + 4 盏灯 + 自适应相机 rig
3. 柜体：4.8×4.0×5.2，落口 1.6×1.5 在 (-1.5, 1.2)
   - 物理：底板拼 4 块（留洞）+ 四壁 + 顶 + 落口井
   - 视觉：柜体/玻璃/立柱/横梁/缆绳
4. 爪头：kinematicPositionBased 刚体
   爪指×2：dynamic + revolute joint + ForceBased 电机
5. 奖品：3 个球体堆的熊（或者直接用 BoxGeometry 占位）
6. 状态机：ready → idle_x → moving_x → idle_z → moving_z → descend → close → lift → home → release
7. 判定：奖品 y < 0.75 且在落口 XZ 范围内
8. HUD：金币 + PLAY 按钮 + 两个方向键
```

**验收**：能完整玩一局，抓到了会消失，没抓到留在原地。

### 阶段 2：手感与多机台

```
1. 加握力模型（eff 公式）→ 偏心抓不住、重的抓不住
2. 加假影（shadowBlob）
3. 加 align 成功锁定 + guidePrize 引导
4. 加 settle 静置判定 + 抖落
5. 把机台参数抽成 MACHINES 数组，加 3 台（不同 armPower / fingerLen）
6. 加布局持久化
```

**验收**：抓正中间的成功率明显高于抓边缘；换机台手感不同。

### 阶段 3：经济与留存

```
1. 金币/券/收益三种货币 + 付费优先级
2. 每日：JST 重置 + 7 天印章 + 3 任务 + 1 挑战（种子随机）
3. 跳蚤市场：价格漂移 + 分段成交概率 + 10% 抽成 + NPC demo
4. 图鉴 + 排行榜
```

**验收**：不投币也能靠卖奖品继续玩；跨天能拿到新任务。

### 阶段 4：表现力

```
1. 音频包（manifest + pack 寻址）或退化成普通 audio 标签
2. 特效（粒子 + 相机冲击 + 顿帧）
3. 中奖彩带、镜头推近、LED 呼吸
4. 三语言
```

### 复刻时必须知道的 8 个坑

| # | 坑 | 后果 |
|---|---|---|
| 1 | 零时间步进 `world.step(0)` | Rapier wasm panic，物理永久失效 |
| 2 | 爪子状态机放在 `world.step` 之后 | 爪子永远慢一帧，抓取判定错位 |
| 3 | `depthWrite:true` 的玻璃材质 | 挡住柜内奖品 |
| 4 | 落口用一整块底板 | 奖品掉不下去（Rapier 没有带洞的 box，必须拼） |
| 5 | 不用假影 | 玩家判断不了 z 轴距离，劝退 |
| 6 | 合爪力量给满 | 永远抓得住，没有可玩性 |
| 7 | BGM 切换不串行化 | 两首同时响 |
| 8 | 相机冲击累加而非单帧 | 相机越飘越远 |

## 17. 该直接改，还是先重构？

### 17.1 结论先行

**看你改什么。** 分三档，不要一刀切。

| 你想做的事 | 建议 | 理由 |
|---|---|---|
| 调数值（价格、难度、时长） | **直接改** | 全在 `config.js`，改完即生效 |
| 加奖品 / 换贴图 / 换配色 | **直接改** | 数据驱动，加个对象就行 |
| 加一台同内核的机台 | **直接改** | 抄一个 config 对象，改 id/价格/prizeId |
| 加文案 / 加语言 | **直接改** | `i18n.js` 加 key |
| 改 UI 布局、加个页面 | **直接改，但要小心** | DOM 是 `innerHTML` 字符串拼的，3000 行里找位置 |
| 改核心玩法（新抓取规则） | **先局部重构** | 状态机是一个 700 行的 switch，加分支会失控 |
| 加联网（真排行榜、真交易） | **重写后端，前端局部改** | 现在 `gp` 是垫片，接口设计得还不错，能对接 |
| 移植到别的引擎（Unity/Godot） | **重写** | 但可以照这份文档搬逻辑 |
| 要上架、要长期迭代 | **重写前端** | 见下 |

### 17.2 为什么"直接改"有天花板

这份代码有三个结构性限制，不是风格问题：

**① 它是编译产物，不是源码**

`game.js` 里有 11 行"纯空白但长度超过 10 字符"的行，合计约 1700 个空格——那是 TypeScript 类型标注被剥掉后留下的位置。原作者的 `.ts` 源文件不在包里。

意味着：

- 拿不到类型定义，所有参数都是隐式 `any`
- 改一个函数签名，编译器不会帮你找调用点
- IDE 的跳转、重命名、找引用全部退化

**② 单文件 3069 行，没有模块边界**

`game.js` 一个文件里塞了：渲染设置、DOM 构建（约 400 行 CSS 字符串 + 约 300 行 HTML 模板）、存档、经济、9 台机的场景构建、状态机、UI 逻辑、音频、特效。唯一的"分块"是 `// ---------- xxx ----------` 注释。

改一处要滚 3000 行；两个人同时改必然冲突。

**③ 特效库是 3.2MB 的压缩黑盒**

`@makeplay/fx` 没法读、没法改、没法 tree-shake。你只能调它的 4 个预设名。想自定义特效就得整个换掉——但那要重写 `fx.play/update/clear/dispose` 四个接口，工作量不大，风险在别处（它同时管着顿帧和相机冲击）。

### 17.3 三种方案对比

| 方案 | 成本 | 适合 | 风险 |
|---|---|---|---|
| **A. 原地改** | 低 | 数值/美术/加机台/加文案 | 超过 ~500 行改动后维护成本指数上升 |
| **B. 先拆架构再改**（拆成 6~8 个模块 + 补类型 + 换掉 fx） | 中（约 2~4 天） | 要持续迭代、多人协作 | 拆的过程会引入回归，且没有测试网兜底 |
| **C. 照文档重写** | 高（约 1~2 周） | 要换引擎 / 要上架 / 要大改玩法 | 手感要重新调，`armPower` 那套公式要重新试 |

### 17.4 我的建议：走 B，但别一次拆完

**第一步：先加护栏，别先动结构。**

在拆之前，把"什么算改坏了"变成可执行的判据：

```
1. 把 config.js 里所有数值导出成一份快照 JSON
   → 改完 diff，确认只有你想改的那几个变了

2. 写一个自动化冒烟脚本（这份项目里已经有可复用的）
   → 无头浏览器 + CDP，检查 window.__gpPlayable === true
   → 进机台 → 检查 prizes.length > 0 且 canvas 尺寸正常
   → 点 PLAY → 检查金币减少、phase 变成 idle_x

3. 抓一版基准截图，改完对比
```

这三步加起来不到半天，但它决定了后面所有改动是"可控"还是"赌运气"。

**第二步：只拆最痛的那一层。**

按"改的频率 × 耦合度"排序，先拆 `game.js` 里最常改的部分：

```
优先级 1：UI 层（约 700 行 CSS + HTML 模板）
  → 抽到 ui/screens.js，用模板函数替代巨型字符串
  → 好处：改界面不再碰游戏逻辑

优先级 2：机台构建（约 900 行 build* 函数）
  → 抽到 scene/machines/，每台一个文件
  → 好处：加机台不用读 3000 行

优先级 3：状态机（约 700 行 switch）
  → 拆成 phase handlers 对象 { ready: fn, descend: fn, ... }
  → 好处：加状态 = 加一个 key，不用改 switch

不建议拆：渲染设置、物理步进
  → 这部分改的频率极低，拆了只是增加跳转成本
```

**第三步：补类型，但只补边界。**

不需要全量 TS 化。只在**模块之间的接口**上加 JSDoc：

```js
/** @typedef {{x:number,y:number,z:number}} Vec3 */
/** @typedef {{id:string, kind:'grab'|'bridge'|'takoyaki'|'sweets', armPower:number}} Machine */
/** @param {Machine} m @param {number} dt */
function craneTick(m, dt) { ... }
```

这样 IDE 至少有补全和跳转，成本不到全量 TS 化的 10%。

### 17.5 什么情况下直接选 C（重写）

满足任意两条，就别救了，照文档重写：

- 要换引擎（Unity / Godot / 原生 App）
- 玩法要大改（比如从"抓"改成"推币"，或加实时对战）
- 要上应用商店（现在这套没有构建链、没有资源压缩、没有错误上报）
- 团队超过 2 人
- 美术资源要全面替换（41 张图全是 1~2MB 的 PNG，没做图集）

最后一条值得单说：现在 `assets/` 是 41 张独立 PNG，总共 63.7MB。**首屏要下载 4 张图（bg-home 2.12 + arcade-backdrop 1.33 + bg-arcade 1.08 + logo 0.66 ≈ 5.2MB）**。如果要做正式产品，这一步必须换成图集 + WebP/AVIF + 懒加载——但那是资源管线问题，改代码解决不了。

### 17.6 一句话回答

> **调数值、换皮、加机台 → 直接改，`config.js` 就是为这个设计的。**
> **加新玩法、多人协作、要上架 → 照这份文档重写前端，但把 `daily.js` / `market.js` / `config.js` 三个纯逻辑文件原样搬走**（它们没有依赖，是这套代码里最干净的部分）。
> **中间地带（改 UI、加状态）→ 先花半天加冒烟脚本和数值快照，再按"UI → 机台 → 状态机"的顺序局部拆，别一次拆完。**
